# 换肤核心集成评估

实施更新：已新增 AntdUI“游戏换肤”菜单、持久化启用开关、C# 服务与原生主机适配，配套文件随 win-x64 运行包外置发布。已接入游戏阶段失效处理。当前支持手动选择与恢复基础皮肤；全英雄清单导出、人工验收数据库、选择自动应用及接入前皮肤快照尚未接入。下文保留原评估方案，建议文件中已实施者以仓库代码为准。

评估日期：2026-10-10。目标项目：`E:\code\weather-app`；核心来源：`E:\tools\LeagueSkinCore`。本轮仅完成源码检查和方案评估，未集成生产代码、未加载游戏核心或执行换肤。

## 当前项目与核心

项目名称虽是 weather-app，但实际内容是 LOL 对局小助手：.NET 10 WinForms、AntdUI，使用 Application、Domain、Infrastructure 分层，通过 `Bootstrap/AppCompositionRoot.cs` 组合服务。`GameMain.cs` 已处理游戏阶段变化，`ClientToolsForm.cs` 是客户端工具页。现有 LCU 客户端背景/头像选择功能与游戏内换肤是两条不同路径，不能复用其写入接口实现游戏内皮肤替换。

独立核心由 x64 C++ DLL、命令行主机和 Python 服务组成。C++ 实现数据库读取、构建指纹校验、会话身份、皮肤及形态更新、实际状态读取；Python 服务负责串行请求、目录条目标识检查、二次结果校验、事件日志和人工验收记录。原生主机通过标准 WH_GETMESSAGE Hook 加载 DLL，stdout 返回 UTF-8 JSON。仅查看其游戏内目录或状态也会加载模块，不能把这类查询视为纯 LCU 查询。

## 推荐方案

采用 **C# 适配服务 + 原生命令行主机 + 同目录 DLL**，复用现有 C++ 换肤实现，把必要的 Python 服务逻辑移植到 C#。不在 WinForms 进程中直接 P/Invoke 换肤函数：当前 DLL 导出的是消息 Hook 回调，并不是可在 UI 进程调用的 ApplySkin SDK。

| 方案 | 成本和边界 | 评估 |
| --- | --- | --- |
| C# 调用原生主机，移植服务逻辑 | 不引入 Python 运行时；需实现请求调度、目录验证与结果校验 | 推荐作为正式集成方案 |
| C# 调用常驻 Python 服务，再转原生主机 | 可保留已有验收记录实现，但需额外打包运行时、RPC 和服务生命周期 | 可作为临时对照实现，正式发布维护成本更高 |
| 直接 P/Invoke 当前 DLL | 当前 DLL 没有对应进程外换肤 API，且游戏函数不能在助手进程直接调用 | 不适用于当前核心接口 |
| 将核心全部重写成 C# | 需要重新处理原生游戏函数、结构布局与生命周期，并重新验证 | 本次集成没有必要 |

## 建议落点

以下文件均为建议新增，当前还不存在：

| 文件/目录 | 职责 |

| `Application/Skins/ISkinCoreService.cs` | Status、Catalog、Apply、Restore 等异步用例；支持 CancellationToken |
| `Domain/Skins/` | 会话、目录条目、实际状态、请求结果模型，明确区分调用与核验结果 |
| `Infrastructure/Skins/NativeSkinCoreService.cs` | 参数校验、进程启动、JSON 解析、全实例串行队列、超时与结果核验 |
| `Infrastructure/Skins/FileSkinAcceptanceStore.cs` | 日志、版本绑定的选择与验收数据；避免与原版记录混用 |
| `BaseViewForm/SkinToolsForm.cs` | 当前英雄、皮肤搜索、形态选择、应用与恢复按钮、明确结果提示 |
| `native/LeagueSkinCore/`（仓库根） | C++ 源码、构建脚本、许可证与构建来源 |
| `LOL-GameAssistant/Tools/SkinCore/` | 发布时的 x64 EXE 与 DLL 配套资源 |

在 `AppCompositionRoot.cs` 注册同一个服务实例，防止页面和状态刷新各建一个队列。`GameMain.cs` 通知阶段变化；LCU 阶段仅用于界面状态，真正可切换状态由核心确认的进程、玩家、指纹及目录决定。皮肤页可以作为设置中的独立分组入口，避免把游戏内切换放进已有客户端背景设置。

## 接口与请求约束

建议 C# 接口：`GetStatusAsync`、`GetCatalogAsync`、`ApplyAsync(session, entryId)`、`RestoreAsync(session)`。全英雄 Inventory 和验收导出后续单独增加，不混入每次页面刷新。

主机现有命令为 `status`、`catalog`、`entry session index gear`、`restore session`、`inventory [index]`。C# 使用 `ProcessStartInfo.ArgumentList` 和绝对路径启动，禁止 shell 拼接命令；异步同时读取 stdout/stderr，解析 JSON 并限制输出大小。

必须移植的保护：

1. 用单实例 `SemaphoreSlim` 串行全部核心请求，包括状态刷新和切换；不并发启动多个主机。重复按钮点击不得形成无界队列。
2. 切换前刷新当前目录，核对会话和具体条目；皮肤编号不唯一时拒绝仅按编号调用。特殊模型与形态依据当前数据库条目选择。
3. 不能仅根据退出码或 JSON `ok` 判断成功。核对 `independent=true`、`original_required=false`、`state_verified`、返回会话和实际皮肤/模型/显式形态；拒绝原版或其他主机的响应。
4. 保留原生请求编号和超时结果。原生等待约 5.5 秒，C# 外层可采用现有 Python 层的 9 秒上限；队列等待应单独支持取消。
5. 执行开始后的取消、杀掉主机或超时，不能保证游戏内动作已停止。显示“结果未确认”，重新读取状态，不自动重试，不把取消显示成已撤回。
6. 阶段结束、进程变化、断线或核心版本变化时禁用应用、清除当前目录与排队选择。开始写入前再校验会话；迟到结果不得覆盖新对局页面状态。
7. 已保存选择绑定核心包版本、游戏配置指纹、英雄和完整条目身份。本次集成应补充明确的核心包版本；当前原生 `reference_sha256` 主要表示游戏配置，不足以单独区分后续算法更新。
8. 日志只存游戏状态、请求编号和失败阶段，不复制 LCU 凭据、卡密或授权信息。

恢复命令当前恢复**基础皮肤及已确认的默认形态**，不是恢复接入前任意付费皮肤的快照。页面应称“恢复基础皮肤”；若产品要求真正恢复接入前状态，需要另做快照实现和形态验收。

## 生命周期和发布

实验功能默认关闭；用户打开皮肤页并主动连接后才允许调用原生查询。不能将核心连接挂到应用启动或现有 LCU 高频轮询。启用后只有一个受控的状态刷新任务，退出页面/对局后停止排队刷新。应用关闭不强制卸载已驻留的游戏内模块。

正式版采用 win-x64 发布。即使主项目 AnyCPU 启动成功，原生主机和 DLL 仍须配套 x64。项目当前存在单文件发布配置；核心两文件应作为明确的外置配套文件发布，避免 DLL 被装入 bundle 后无法由主机按相邻路径找到。后续如坚持单文件，需要另做按版本和哈希提取至应用自有缓存目录的逻辑。

通过 csproj 的 CopyToOutputDirectory / CopyToPublishDirectory 和 ExcludeFromSingleFile 配置打包，保留许可证与哈希清单，避免引用 `E:\tools` 绝对路径。发布机无需 Python；编译核心时需要 C++ Build Tools / Windows SDK。

不在第一次读取失败时自动请求管理员权限，不修改游戏安全设置。Windows 拒绝 Hook、版本不支持、字段读取失败都应作为可理解的失败状态返回。

## 实施顺序与验收

1. **适配层与假主机测试**：增加 DTO、服务、命令白名单、队列与会话规则；用假主机模拟超时、退出、非法 JSON、读回不匹配、旧会话、取消和连续请求，不依赖实际游戏。
2. **界面和生命周期**：独立皮肤页与默认关闭开关；游戏退出禁用操作；新对局清理旧选择；覆盖主题、中英文、页面销毁后的迟到结果。
3. **发布检查**：在不依赖源码目录、Python 或 E:\tools 的环境检查运行包文件和错误提示；核对 EXE/DLL 哈希及许可证。
4. **游戏内验收**：已适配构建上验证普通皮肤、重复编号、特殊模型、基础皮肤恢复；再按既有全英雄计划验证技能、攻击、回城、复活、连续切换和长时间特殊形态。状态校验通过不能替代视觉和稳定性验收。

本次抽离已有 17 项 Python 接口测试及原生夹具测试通过，但抽离包没有重新完成真实游戏验收，完整全英雄与特殊形态验收仍待完成。其原生配置当前绑定 PE 时间戳 `1790968218`、映像大小 `35241984`；更新的游戏构建必须重新适配，不能靠集成代码自动获得兼容。

已知仓库有用户未提交的 `CoachForm.cs` 和 `CoachThemeTests.cs` 修改。实际实施应保留这些修改，并避免通过整个目录覆盖导入旧项目。

## 评估结论

技术上可集成，架构匹配度较高。工作量重点在 C# 请求和生命周期适配、发布以及真实游戏验收，而不是换肤算法重新实现。先完成受控手动切换，再考虑自动应用已保存选择。

集成不会增加官方授权或降低已知账号处罚风险。现有核心没有防检测功能；不能将助手已有 LCU 能力的边界推广到游戏内内存换肤。账号风险说明见已有检测审查和腾讯官方换肤处罚公告。
