# 换肤特效同步排查与修复

日期：2026-10-10。范围为 weather-app 的独立一代核心；二代恢复继续暂停。

## 已确认的缺漏

原来的 `independentWriteSkin` 更新玩家加密皮肤字段和基础皮肤编号，随后调用游戏 Update。非空 CharacterDataStack 的皮肤层编号没有同步。回读只检查基础编号、模型名称和基础形态；同一个模型的不同皮肤无法靠模型名称区分，因此可能在实际层仍为旧编号时显示核验通过。

用户提供的原版一代 R3nzSkin.dll（SHA256 `87d29e8391c7492251c4df857a7e177720f901feb6c84d4bf156c0a9f748534d`）在 RVA `0x55ecd` 读取基础编号 `[r9+0x38]`，在 `0x55ed1` 比较层编号 `[r11+0x20]`，在 `0x55ed7` 写回，随后以 `true` 调用 Update。它在周期处理里补偿不一致的皮肤层。公开参考 Hooks.cpp 也存在该逻辑，但本次结论以原版机器码为证据。

已有已检查游戏构建的 Update 指纹（RVA `0x21cc90`）显示：有皮肤层时选取 `end-0xa0`，为空时使用 `stack+0x18` 的基础数据。因此只核验基础编号不够。游戏文件的时间戳和映像大小仍对应已有构建；磁盘文件该位置不是可用明文指令，本次没有将磁盘字节当作新的动态布局证据。仍沿用既有版本指纹检查，未知版本停止调用。

## 本次修改

- 换肤前验证整个层向量的长度、容量、模型字符串和编号范围；活动层模型不匹配时拒绝调用，避免向借用模型写入别的模型的皮肤编号。
- 在原有 Update 前同步与目标模型相同的皮肤层编号，保留其他模型的层；拉克丝、娑娜仍通过既有清理/Push 路径切换特殊模型。
- 原生响应增加 `active_skin`，核验同时要求基础编号、加密编号、活动层编号和目标模型一致。
- C# 服务要求 `active_skin` 匹配；旧 DLL 缺失该字段、或活动层仍为旧编号时，不显示核验成功。日志增加活动层编号，不记录卡密。
- 不增加周期游戏钩子、不修改数据库条目、不新增未确认的资源重载调用。

## 验证与实际限制

原生测试覆盖空栈、同模型旧编号同步、多层同步、不同模型保留、活动模型不匹配、还原编号、非法编号和向量边界；C# 定向测试覆盖活动层旧编号及字段缺失时拒绝成功判定。

本轮结果：原生编译及测试通过；换肤服务 17 项定向测试通过；换肤页面 7 项定向 UI 测试通过；win-x64 自包含运行包发布成功，输出为 `artifacts/skin-integration/LOL-GameGUI.exe`。主程序和外置 `Tools/SkinCore` 需要一起保留。

这些测试验证皮肤状态同步与失败处理，不证明粒子、音效和回城已在游戏内恢复。若故障发生时皮肤栈为空，本次同步补丁不会改变该路径，也不能将全部现象归因于此缺漏。英雄召唤物、被动产生的新对象及后续变身的持续同步仍未补齐。

复测须退出旧对局，在新版助手中连接新的练习模式。确认一款本来具有独立特效的皮肤，记录英雄、皮肤、`skin` / `active_skin` / `active_model`，重新释放技能、普攻、回城，并比较声音。已有粒子不作为新技能验收依据。仍有缺项时继续追踪实际资源刷新链，不能标记全英雄或全部特效通过。
